# 租户投影对账回流 + AppAuth 闸门启停校验（租户事实端原则的收口）

## 问题

租户的「平台为事实端」在写路径早已成立（平台先行/本地跟随/失败回滚），但存在两个缺口：
1. **读面漂移**：平台管理端直接改租户（改名/启停/新建/删除）不回流本地投影，service 显示旧数据且无告警，直到手动 sync；
2. **闸门语义缺口**：AppAuth 闸门只校验租户存在性，不校验启停——停用租户的 App 流量仍可通行。

## 提案 / 决策

**采用 A+（约定 + 对账回流）而非 B（管理页实时代理）**：B 只买到显示层真相（闸门/映射仍走投影），代价是列表跨服务延迟 + 平台故障影响面扩大到读。A+ 让投影语义补完整（写穿 + 回流），读路径保持本地快读。

1. **对账回流任务**（`biz/tenant.ReconcileFromPlatform`，job handler `tenant_reconcile`，cron `*/5`）：
   分页拉平台商户租户全量 → 本地跟随（平台新建→补建、资料/启停变更→覆盖、平台已删→软删+墓碑）；
   未同步存量（platform_id=0，补链域）不参与；单项失败记日志继续；平台拉取失败整体失败下轮重试。
   **护栏**：平台拉取成功但结果为空时跳过下线阶段——空结果无法区分「真清空」与「列表接口异常」，批量下线不可逆，宁可下轮带上非空真相（防误删）。
2. **闸门启停校验**（`middleware.AppAuth`）：本地租户 `!Enabled()` 与未归属/未同步同文案 403（不泄露细节）；
   停用生效链路 = 平台停用 →（≤5min 对账回流）本地停用 → 闸门拒绝。
3. **顺手修复存量断线**：job 体系（种子+cron 调度器）`EnsureSeededAndStart` 从未被调用——
   接入 `NewHTTPServer` 构造（失败不阻断 HTTP，记错误日志）并在 `Stop` 优雅停调度器。
   此前所有内置清理任务（日志/导出/用量/告警）同样从未运行，本修复一并激活。

## 真实考虑过的备选

| 备选 | 放弃理由 |
|---|---|
| B：管理页租户列表实时代理（同 app-user 模式） | 只买到显示层真相；列表延迟 + 平台故障影响面扩大到读；闸门/映射仍依赖投影 |
| 对账不做删除跟随（只增改不删） | 平台侧删除后本地投影永残留，租户 code 唯一槽位被墓碑占用以外的活行占住 |
| 空结果照常下线 | 列表接口异常返回空会触发批量误删（不可逆）；「平台真清空」可由下一轮非空确认兜住 |

## 验收标准

- [x] 单测：对账四语义（改名/停用回流、平台新建补建、平台已删下线、未同步不动）+ 空平台护栏保住本地
- [x] 闸门单测：本地已停用租户 403（新增用例，矩阵其余不变）
- [x] 端到端（平台 :27080 + 本服务 :28180 实测）：
  - 闸门：本地停用 403 → 恢复 200；
  - 种子任务落库（*/5）+ cron 实际触发（17:45/17:50 两轮）；
  - 平台侧改名 → **17:50 tick 自动回流本地**（job_logs：平台 1、更新 1）；
  - 平台真相为 0 + 本地残留 1 条 → 对账正确下线（17:45 轮）；
  - 租户删除遇关联用户 409 守卫（平台侧 ErrTenantInUse 链路）。
- [x] `make test`/`go vet`/gofmt 全绿；冒烟数据已清理。

## 补充：job 执行链健壮性收口（同日）

激活 job 体系后审计发现并修复三处执行链缺陷：

1. **panic 无隔离**：handler panic 发生在 cron/手动触发的 goroutine 内，会打死整个进程
   （cron 链只挂了 SkipIfStillRunning，未挂 cron.Recover；RunOnce 是裸 `go execute`）。
   修复：`runHandler` defer-recover，转失败日志（含堆栈）。
2. **RunOnce 绕过互斥**：cron 的 SkipIfStillRunning 只对调度触发生效，手动触发可与
   cron tick/彼此重叠——对账类任务重叠会双拉双写。修复：Usecase 内 `running` 原子占位
   （cron/手动共用），在跑时调度跳过并记日志、手动返回 `ErrJobRunning`。
3. **Stop 无界等待**：cron.Stop 的等待 ctx 在跑任务不结束就不返回（最坏卡到 10 分钟
   执行超时）。修复：有界等待 15s 后放弃（任务幂等，下次启动重跑）。

已确认无需处理：job_logs 无限增长（execute 每次顺带 CleanupLogsBefore 30 天，started_at 有索引）、
执行超时（execTimeout=10min 全局约束）、种子 cron 后续调整不回写存量库（按需手动改任务，
幂等跳过是设计行为）、多实例部署无分布式锁（entity.go 已声明单机语义，扩副本时需另立决策）。

## 风险与后果

- 漂移上界 = 对账周期（5 分钟）+ 平台侧无变更事件推送（若将来要秒级，需平台出变更通知，另立决策）。
- 对账每 5 分钟一次开放面全量拉取（商户租户量级小，分页 100/页，开销可忽略）。
- job 体系激活后，此前从未运行的四类保留期清理任务开始生效——存量数据首次清理可能出现一次批量删除（保留期参数见各自配置）。
